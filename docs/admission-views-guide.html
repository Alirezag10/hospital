راهنمای خط‌به‌خط Viewهای پذیرش

تحلیل شش فایل پذیرش در Yii 2، همراه با ارتباطشان با Controller، Model، پایگاه داده و JavaScript

نقشهٔ کلی و مسیر اجرای پذیرش

Yii از الگوی MVC استفاده می‌کند. Viewها HTML را می‌سازند، اما تصمیم‌های اصلی مانند اعتبارسنجی، جست‌وجو و ذخیره‌سازی در Controller و Model قرار دارند. فایل‌های این گزارش در app/views/admission/ هستند.

View: فرم، جدول، تقویم و جزئیات قابل مشاهده
Controller: AdmissionController؛ آماده‌سازی داده و پاسخ به درخواست
Model: Admission و AdmissionSearch؛ قوانین، روابط و Query
رابط مرورگر: app/web/js/patient-search.js و CSSهای پروژه
Browser → URL Rule / Route → AdmissionController Action → Model / Query → Database → render(View) → HTML Response

در جست‌وجوی زنده، مسیر جداگانه‌ای داریم: مرورگر با fetch() به Action جست‌وجو درخواست می‌فرستد؛ Controller پاسخ JSON می‌دهد؛ JavaScript گزینه‌ها را در فهرست کشویی می‌سازد. انتخاب نهایی با ارسال فرم به سرور می‌رسد و Model دوباره شناسه‌ها را اعتبارسنجی می‌کند.

ترتیب خواندن پیشنهادی: create.php برای ورود، _form.php برای ثبت، index.php و _search.php برای فهرست، سپس calendar.php و view.php.

تحلیل بخش‌به‌بخش خطوط

خطکد/بخشتوضیح و دلیل
1–8useها و DocBlockPatient، Doctor و Ward برای خواندن سوابق انتخاب‌شده؛ ArrayHelper برای ساخت گزینه‌های بخش؛ Html برای تولید HTML امن؛ Url برای ساخت URL مطابق تنظیمات Yii؛ ActiveForm برای ساخت فرم متصل به Model. DocBlock فقط به IDE می‌گوید نوع $model و $patientLocked چیست و در زمان اجرا قانون امنیتی ایجاد نمی‌کند.
9–18شناسه‌ها، خواندن رکوردهای انتخاب‌شده و فهرست بخش‌هاfilter_var(...FILTER_VALIDATE_INT...) شناسه را عدد صحیح مثبت می‌کند؛ اگر معتبر نباشد false برمی‌گرداند و Query اجرا نمی‌شود. findOne() بیمار/پزشک را از DB می‌خواند تا متن اولیهٔ ورودی قابل نمایش باشد. ArrayHelper::map() داده‌های بخش را به آرایهٔ id => label برای منوی انتخاب تبدیل می‌کند. تابع static fn برای افزودن طبقه به برچسب هر بخش است.
19–22باز کردن کارت و ActiveFormActiveForm::begin() تگ form و اتصال آن به مدل را آغاز می‌کند. ویژگی‌های data-loading-form و data-unsaved-warning برای JavaScript رابط استفاده می‌شوند؛ خودشان به‌تنهایی اعتبارسنجی امنیتی نیستند. errorSummary() خطاهای مدل را در یک محل نشان می‌دهد.
23–47انتخاب بیمارfieldset/legend گروه معنایی و قابل‌دسترس می‌سازند. Hidden input مقدار واقعی patient_id را می‌فرستد. اگر $patientLocked و بیمار موجود باشد، ورودی فقط‌خواندنی است؛ وگرنه ورودی جست‌وجوی زنده ساخته می‌شود. data-search-url مقصد AJAX را از Route می‌گیرد؛ data-target-input مشخص می‌کند شناسهٔ منتخب در کدام hidden input نوشته شود. aria-controls و aria-expanded وضعیت فهرست نتایج را برای فناوری‌های کمکی بیان می‌کنند. خروجی جست‌وجو ابتدا hidden است و JS هنگام دریافت نتایج آن را باز می‌کند.
48–79پزشک و بخششناسهٔ پزشک نیز hidden است و ورودی قابل مشاهده تنها عبارت جست‌وجو را می‌گیرد. JS از search-doctors نتیجه می‌گیرد و شناسهٔ انتخاب‌شده را در hidden input قرار می‌دهد. بخش برخلاف پزشک با dropDownList() ساخته می‌شود؛ گزینه‌ها از Query بالا آمده‌اند. متن «تاریخ پذیرش خودکار...» توضیح رابط است؛ مقدار واقعی تاریخ و وضعیت را Model در beforeSave() تنظیم می‌کند، نه این متن.
80–98دکمه‌ها و پایان فرمدکمهٔ submit فرم را ارسال می‌کند. data-loading-label برچسب زمان ارسال برای اسکریپت UI است. لینک انصراف GET به فهرست می‌رود. ActiveForm::end() تگ فرم و اسکریپت‌های لازم Yii را می‌بندد.

نکات مهم و بهبودپذیر

  • قفل‌کردن بیمار در مرورگر به‌تنهایی کافی نیست؛ Controller هنگام وجود patient_id در URL آن را پس از load() دوباره روی مدل می‌گذارد. این کار مانع دست‌کاری hidden input برای جایگزین کردن بیمار می‌شود.
  • در هر نمایش فرم چند Query برای بیمار، پزشک و همهٔ بخش‌ها اجرا می‌شود. در حال حاضر قابل‌قبول است؛ اگر داده زیاد شد، برای بخش هم جست‌وجوی AJAX یا صفحه‌بندی لازم می‌شود.
  • required روی input مرورگر فقط تجربهٔ کاربر را بهتر می‌کند. الزام واقعی شناسه و وجود بیمار/پزشک/بخش در قانون‌های Model و کلید خارجی DB است.

app/views/admission/_search.php Partial View / فیلتر GET

وظیفه: ساخت فرم جست‌وجوی پذیرش‌ها
فراخوان: index.php
مدل: AdmissionSearch؛ مدل جست‌وجوست و ActiveRecord نیست
خروجی: query string مثل ?AdmissionSearch[name]=...
خطکد/بخشتوضیح
1–5وابستگی‌ها و قرارداد ورودیHtml برای دکمه‌ها و لینک‌ها و ActiveForm برای فیلدهای متصل به مدل. DocBlock نوع AdmissionSearch را برای IDE مشخص می‌کند.
6–9فرم جست‌وجوکلاس‌های Bootstrap چیدمان ستون‌ها را می‌سازند. method => get فیلترها را در URL قرار می‌دهد؛ در نتیجه لینک جست‌وجو قابل ذخیره و بازتولید است. action => index درخواست را به Action فهرست می‌فرستد. اعتبارسنجی سمت کاربر خاموش شده تا قواعد جست‌وجو روی سرور مرجع باشند.
10–14نام، کد ملی، موبایل، وضعیتfield() از attributeLabels() و قواعد مدل برای برچسب/خطا استفاده می‌کند. وضعیت فقط دو گزینهٔ مجاز «بستری» و «ترخیص‌شده» دارد؛ prompt یعنی هیچ فیلتر وضعیتی انتخاب نشده. dir=ltr و inputmode ورود شناسهٔ عددی را راحت‌تر می‌کند.
15–19خطاها و دکمه‌هاerrorSummary() خطاهای ورودی را نشان می‌دهد. submit پارامترهای GET را می‌فرستد؛ لینک پاک‌کردن به index خالی می‌رود. هیچ Query مستقیمی در View انجام نمی‌شود.
20–28نمایش فیلترهای فعالpartial مشترک layouts/_filters نام و مقادیر فیلترها را برای حذف سریع نمایش می‌دهد. برای status، مقدار داخلی انگلیسی به برچسب فارسی تبدیل می‌شود. is_string قبل از map کردن، از دسترسی نامعتبر به آرایه جلوگیری می‌کند.
مشکل پیدا و اصلاح‌شده در تست پروژه: فیلتر موبایل ابتدا در محاسبهٔ $hasFilters لحاظ نمی‌شد و پیام حالت خالی اشتباه بود. اکنون شرط $searchModel->mobile را هم بررسی می‌کند؛ تست فیلتر موبایل بدون نتیجه موفق گذشت.

app/views/admission/calendar.php View / تقویم شمسی

وظیفه: نمایش پذیرش‌ها در روزهای ماه شمسی
داده از: AdmissionController::actionCalendar()
مدل مرتبط: Admission با رابطهٔ patient
تعامل: لینک ماه قبل/بعد و لینک هر پذیرش
خطکد/بخشتوضیح
1–8عنوان و محاسبات اولیهHtml برای خروجی امن است. title و breadcrumb عنوان صفحه را می‌سازند. $cellCount تعداد خانه‌ها را به مضرب هفت می‌رساند تا هفتهٔ آخر کامل شود. نام ماه‌ها آرایهٔ فارسی است. پارامتر $month از Controller به صورت سال-ماه می‌آید و با explode به دو بخش عددی تبدیل می‌شود.
9–14ارقام و عنوان ماهتابع کوتاه $persianDigits رقم‌های انگلیسی را برای نمایش به فارسی تبدیل می‌کند؛ مقدار اصلی تاریخ دست‌کاری نمی‌شود. عنوان ماه از آرایهٔ ماه‌ها و سال فارسی‌شده ساخته می‌شود.
15–26سربرگ و پیمایش ماهHtml::encode() عنوان را قبل از درج در HTML escape می‌کند. لینک‌ها Route تقویم را با پارامترهای previousMonth و nextMonth باز می‌کنند. این محاسبات در Controller انجام شده؛ View فقط مقدار آماده را نمایش می‌دهد.
27–29سرستون روزهای هفتهحلقهٔ foreach هفت نام روز را به ترتیب می‌سازد. role=grid و columnheader نقش اجزا را برای فناوری‌های کمکی مشخص می‌کنند.
30–49خانه‌های روز و رویدادهاحلقهٔ سلول‌ها با $startOffset و $daysInMonth شماره روز را حساب می‌کند؛ خانه‌های بیرون ماه مخفی/غیرفعال‌اند. برای روز معتبر، کلید میلادی Y-m-d از $firstDay->modify() محاسبه می‌شود تا با کلیدهای گروه‌بندی Controller تطبیق کند. حداکثر سه پذیرش در هر روز نمایش داده می‌شود؛ رویدادهای بیشتر با شمارنده خلاصه می‌شوند. هر رویداد به view همان پذیرش می‌رود. نام بیمار encode می‌شود و نام پزشک/بخش در title لینک قرار می‌گیرد.
مفهوم تقویم: دیتابیس تاریخ میلادی نگه می‌دارد؛ Controller بازهٔ شروع و پایان ماه شمسی را با JalaliDate به میلادی تبدیل می‌کند و Query بازه‌ای می‌زند. View فقط تقویم شمسی می‌سازد. شرط بازهٔ >= شروع و < پایان ماه بعد برای استفادهٔ مناسب از ایندکس تاریخ بهتر از تبدیل تک‌تک تاریخ‌های ستون در WHERE است.

وابستگی‌های Yii و بک‌اند که برای فهم این Viewها لازم است

  • AdmissionController::actionIndex() مدل AdmissionSearch را می‌سازد و نتیجهٔ search() را به index می‌دهد.
  • AdmissionController::actionCreate() فرم را رندر می‌کند؛ در POST، load() فقط ویژگی‌های safe را پر می‌کند و save() قوانین مدل را اجرا می‌کند. اگر بیمار از URL انتخاب شده باشد، شناسه پس از load دوباره روی مدل قرار می‌گیرد.
  • Admission::rules() الزامی بودن شناسه‌های بیمار/پزشک/بخش و وجود رکوردهای مرجع را بررسی می‌کند. در beforeSave() نام پزشک و بخش و زمان/وضعیت اولیه برای ثبت تاریخی snapshot می‌شوند.
  • جست‌وجوی زندهٔ بیمار و پزشک به actionSearchPatients() و actionSearchDoctors() می‌رسد؛ این Actionها JSON می‌دهند. patient-search.js با debounce ۲۵۰ میلی‌ثانیه‌ای از درخواست‌های زیاد جلوگیری می‌کند، درخواست قبلی را abort می‌کند و انتخاب را در hidden input ثبت می‌کند.
  • HospitalFormatter نمایش عدد و تاریخ را هماهنگ می‌کند؛ JalaliDate تبدیل تاریخ تقویم فارسی سمت سرور را انجام می‌دهد. تنظیم locale و timezone در app/config/web.php است.
  • Viewها خروجی‌اند، نه مرجع امنیت. Queryها parameterize می‌شوند چون Yii Query Builder از آرایه‌های شرطی استفاده می‌کند؛ با این حال هر متن پویا در HTML باید encode شود. استفادهٔ درست از Html::encode() در خروجی‌های حساس XSS را کاهش می‌دهد.

جریان نمونه: ثبت پذیرش از صفحهٔ بیمار

1) Patient page → /admission/create?patient_id=… → 2) actionCreate validates patient id → 3) create.php renders _form.php → 4) JS finds doctor / form submits IDs → 5) controller restores locked patient ID → 6) Admission rules + beforeSave → 7) INSERT database → redirect to view

چکیدهٔ اصلاح‌های پیشنهادی

  1. اصلاح انجام‌شده: شرط $hasFilters اکنون موبایل را هم لحاظ می‌کند.
  2. در صورت رشد تعداد بخش‌ها، dropdown بارگذاری همهٔ بخش‌ها را به جست‌وجوی AJAX یا محدودسازی تبدیل کنید.
  3. Query خدمات را در صورت نیاز از View به Controller منتقل کنید تا View فقط نمایش‌دهنده بماند.
  4. در محیط Production مطمئن شوید Debug Toolbar و پیام خطاهای فنی عمومی در دسترس کاربران عادی نیستند؛ پیکربندی پروژه IP محلی را برای debug محدود کرده است.

این گزارش مطابق فایل‌های موجود پروژه در زمان بررسی تهیه شده است. فایل‌های View نسخهٔ HTML را تولید می‌کنند؛ قواعد پایگاه داده، کنترل دسترسی و اعتبارسنجی نهایی در مسیرهای سرور قرار دارند.
